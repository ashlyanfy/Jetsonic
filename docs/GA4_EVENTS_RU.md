# Справочник событий GA4 — jetsonic.aero

Что именно отправляет [`frontend/analytics.js`](../frontend/analytics.js).
Настройка самого интерфейса GA4 (роли, фильтры, хранение данных,
пользовательские параметры) выполняется вручную в консоли Google Analytics.

Каждое событие дополнительно несёт `page_type` и `page_language`, поэтому в
таблице они не повторяются.

---

## Просмотры и чтение

| Событие | Когда | Параметры | Повтор |
|---|---|---|---|
| `page_view` | Загрузка любой страницы | `content_group`, `page_type`, `page_language` | 1 на загрузку |
| `scroll_depth` | Прокрутка достигла порога | `percent_scrolled` (25/50/75/90) | по 1 на каждый порог |
| `section_view` | Блок страницы показался на экране на 20% | `section_id`, `section_position` | 1 на блок |
| `page_not_found` | Открыт несуществующий адрес | `not_found_path`, `not_found_referrer` | 1 на загрузку |

`scroll_depth` не срабатывает на страницах короче экрана: там прокрутки нет, и
отдавать по ним 100% значило бы утопить реальную глубину чтения длинных страниц.

**Про `section_id`.** Атрибут `id` есть только у формы (`rfq`), поэтому имя
секции выводится из её заголовка: «A structured entry point for urgent AOG» →
`a_structured_entry_point_for_urgent_aog`. Берётся английский текст из
атрибута `data-en`, а не видимый — иначе арабская версия дала бы той же секции
второе имя, и в отчёте она развалилась бы на две строки. Имена обрезаются до
40 символов.

Если понадобится короткое читаемое имя — достаточно проставить `id` нужной
секции в вёрстке, код возьмёт его вместо заголовка.

## Обращения

| Событие | Когда | Параметры |
|---|---|---|
| `whatsapp_click` | Клик по любой ссылке `wa.me` или `whatsapp.com` | `contact_channel=whatsapp`, `link_placement`, `link_text`, `link_url` |
| `phone_click` | Клик по `tel:` | `contact_channel=phone`, `link_placement`, `link_text` |
| `email_click` | Клик по `mailto:` | `contact_channel=email`, `link_placement`, `link_text` |

`link_placement` принимает значения: `hero`, `header_nav`, `mobile_nav`,
`header`, `footer`, `contact_card`, `cta_band`, `form`, `body`. По нему видно,
какая именно кнопка WhatsApp работает — в подвале, в карточке контактов или в
нижнем меню телефона.

Эти события **не** схлопываются: два клика — два события. Повторное обращение
означает повторное намерение.

## Навигация и интерфейс

| Событие | Когда | Параметры |
|---|---|---|
| `cta_click` | Клик по `.nav-cta`, `.footer-cta`, ссылке в `.cta-band`, `.button` | `cta_text`, `cta_placement`, `link_url` |

## Форма RFQ

| Событие | Когда | Параметры |
|---|---|---|
| `form_start` | Первый клик в любое поле формы | `form_name=jetsonic_rfq` |
| `rfq_attachment_added` | Прикреплён файл | `file_extension`, `file_size_kb` |
| `rfq_submit` | Нажата отправка (попытка) | `request_type`, `urgency`, `aircraft_type`, `has_attachment`, `has_alternate_pn`, `entry_page` |
| `rfq_error` | API отказал или сеть отвалилась | `error_type`, `error_status`, `error_message` |
| `generate_lead` | **Заявка принята.** Только на `/thank-you.html` | те же, что у `rfq_submit` |
| `form_abandon` | Уход со страницы с начатой, но не отправленной формой | `last_field` |

### Как гарантируется, что заявки не задваиваются

Цепочка событий устроена так:

1. При отправке формы код кладёт детали заявки в `sessionStorage` и шлёт
   `rfq_submit`.
2. Обёртка над `fetch` следит за ответом `/api/v1/leads`. Если API вернул
   ошибку — уходит `rfq_error`, **а заготовка из `sessionStorage` стирается**.
3. `app.js` уводит на `/thank-you.html` только при успехе.
4. На странице благодарности код читает заготовку, **сразу её удаляет** и шлёт
   `generate_lead`.

Что из этого следует:

- обновление `/thank-you.html` не создаёт вторую заявку — заготовка уже стёрта;
- прямой заход на `/thank-you.html` по закладке или из поиска не создаёт заявку
  вовсе — заготовки нет;
- упавшая отправка не превращается в заявку, даже если человек потом сам
  наберёт адрес страницы благодарности.

Сравнение `rfq_submit` и `generate_lead` даёт долю технических отказов. Расхождение
больше нескольких процентов — повод смотреть логи `landing-api`.

### Боты

Поле `bot-field` в форме — ловушка: человек его не видит, бот заполняет. Если
оно непустое, **все события заявки подавляются целиком** — и `rfq_submit`, и
`rfq_error`. Второе важно отдельно: бот, долбящий упавший эндпоинт, иначе надул
бы счётчик ошибок и сравнение попыток с заявками перестало бы что-либо значить.

Флаг сбрасывается на следующей отправке, поэтому человек, заполнивший форму
после бота в том же окне, считается нормально.

## Собственные события со страниц

Код выставляет наружу `window.jetsonicTrack`, чтобы блоки, добавленные через
CMS, могли отчитываться без правки `analytics.js`:

```js
jetsonicTrack('brochure_download', { brochure_name: 'aog_service' });
```

Функция существует всегда — в том числе когда сбор выключен (отказ, локальная
разработка, бот). В этом случае она просто ничего не делает, поэтому вызов на
странице безопасен и не требует проверок.

Третий аргумент задаёт защиту от повторов:

```js
jetsonicTrack('video_play', { video_id: 'hangar' }, { once: 'video_hangar' });
```

## Пороги и лимиты

| Что | Значение | Где менять |
|---|---|---|
| Пороги прокрутки | 25, 50, 75, 90 | `SCROLL_STEPS` в `analytics.js` |
| Максимум событий секций на страницу | 20 | `MAX_SECTION_EVENTS` |
| Порог видимости секции | 20% | аргумент `threshold` в `initSectionViews` |
| Минимальная прокручиваемая высота | 200 px | проверка `scrollable < 200` |
| Обрезка текстовых параметров | 100 символов | функция `clean` |
| Боевые хосты | `jetsonic.aero`, `www.jetsonic.aero` | `PRODUCTION_HOSTS` |

## Служебные параметры адреса

| Параметр | Действие | Живёт |
|---|---|---|
| `?ga_debug=1` | Показывать события в DebugView; разрешить отправку с любого хоста | одна загрузка |
| `?ga_internal=1` | Пометить устройство как внутреннее (`traffic_type=internal`) | до отмены |
| `?ga_external=1` | Снять метку внутреннего устройства | — |
| `?ga_optout=1` | Полностью выключить сбор на этом устройстве | до отмены |
| `?ga_optin=1` | Вернуть сбор | — |
